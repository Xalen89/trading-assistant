# Quant workbench — Selected-universe momentum (id: `momentum`)

## Scope and how to read this guide

This is a read-only audit of `lib/trading/quant-momentum.ts` and `tests/trading/quant-momentum.test.ts`. The implementation is a synchronous, bounded calculation over series supplied to it: it does not fetch, synthesize, or forecast data. The assigned files contain the calculation and its unit tests, not the rendered workbench screen, so exact on-screen labels, button placement, whether a field is editable, and actual device behavior cannot be verified here. “Location” below identifies the logical workbench area and the source implementation, not a claim that a particular control is currently rendered. No shared workbench UI/API diagnostics were performed.

Per the task context this is an owner-only, paper-only capability. The calculation itself has no brokerage/execution call. It returns an optional paper allocation preview; it does not place orders, create a queued order, or implement multi-leg order execution.

## What the capability does

At each eligible shared closed-bar timestamp, it calculates trailing bar momentum (`close_now / close_lookback_bars_ago - 1`) for each supplied asset, ranks the fixed universe from strongest to weakest (ties sort by symbol), and computes trailing realized volatility as the population standard deviation of the trailing log returns. It selects positive-momentum names from the top quintile and negative-momentum names from the bottom quintile (at least one candidate per side when the universe is that small); selected names are inverse-volatility weighted. If both sides have candidates, each side receives half of gross exposure; if only one side has candidates, that side receives all gross exposure. Code: `quant-momentum.ts:223-279`, `281-318`.

It also walks a simplified close-to-close exploratory equity path, changing target weights on the configured bar cadence and charging only the supplied fee-plus-slippage assumption against absolute weight turnover. It emits latest rank/direction signals, diagnostic metrics and (when eligible) paper allocation legs. This is arithmetic, not an execution-quality or performance-validation engine. Code: `quant-momentum.ts:455-654`, `684-723`.

## Inputs and practical use

There is no verified UI tap sequence in the audited files. The following is the practical sequence implied by the runner's actual input contract; it should not be read as proof that each field is exposed as an app control:

1. In the Quant workbench, choose the Momentum family (`family: "momentum"`). The exact screen label/control is not visible in the audited source.
2. Supply a fixed universe of **2–8 distinct symbols**, each with a non-empty source label, provenance (`provider` or `user-import`), one common supported timeframe (`1m`, `5m`, `15m`, `1h`, `4h`, `1d`, `1w`), a positive `fetchedAt` in milliseconds, and timestamped candle closes. Use completed bars with positive closes. The runner consumes only supplied data; it has no data-picker/provider-fetch implementation in this module.
3. Supply `now` as a current Unix timestamp in milliseconds. A bar is retained only when `bar.time + timeframe_seconds <= min(now, fetchedAt)` (bar times are Unix seconds). Do not treat an open, future, or post-fetch bar as usable.
4. Set the accepted parameters: `lookback` (integer 2–252 bars), `holdingBars` (integer 1–252 bars), `startingEquity` (finite and positive), and `feeBps` and `slippageBps` (finite and non-negative). Costs are assumed inputs; the code invents no venue fee. Although the shared input type/test fixture includes other fields (`entryZ`, `exitZ`, `inventory`, `orderSize`, `maxInventory`), this runner does not read them; do not assume they affect Momentum.
5. Run the calculation using the workbench's actual UI, if available. Review status and data-quality diagnostics first; then inspect the latest signals, cost/equity metrics and any paper allocation. A `ready` result is not validation or a trade instruction.

For any candidate output intended for further paper evaluation, first confirm the symbols, timestamp provenance, timeframe alignment, corporate-action treatment, and fee/slippage assumptions; then independently validate out of sample before interpreting performance. A flat latest signal means the latest scheduled rebalance has no selected targets, not that the runner recommends a trade.

## Status meanings and insufficient/no-signal cases

- **`ready`**: the runner produced at least one actionable rebalance with a later shared closed bar to mark an exploratory interval. It still sets `validation.status` to **`unconfirmed`**.
- **`insufficient-data`**: fewer than two assets, malformed data, duplicate symbols, mixed timeframes, too few valid/shared closed bars, or no completed actionable rebalance. The returned reasons identify the gate. At a candidate time, snapshots are skipped if an asset lacks a matching timestamp/lookback or has effectively zero/non-finite trailing volatility. No positive top-quintile or negative bottom-quintile momentum target also means no actionable rebalance; if no completed one exists, the result is insufficient-data.
- **`unavailable`**: wrong family, invalid/nonpositive current timestamp, invalid/out-of-range settings, or more than eight assets. Fewer than two assets is insufficient-data; more than eight is unavailable.
- **No selected target at the latest scheduled rebalance**: each latest signal can be `flat` and the paper plan is absent. This is not a buy/sell recommendation, nor proof the strategy has no value. If an earlier rebalance was actionable and completed, the overall calculation may still be `ready`.

## Operational readiness is not empirical validation

The implementation produces deterministic outputs from the supplied series, filters incomplete bars and reports its assumptions. Those are operational calculation properties only. It does **not** establish profitability, predictive power, survivorship-free performance, realistic fills, risk-adjusted superiority, or suitability. The associated test file explicitly labels its synthetic fixtures as arithmetic-only and not performance evidence (`quant-momentum.test.ts:9`); fixture passes are not device proof or a statistical edge. No simulated or fixture data establish any performance claim.
