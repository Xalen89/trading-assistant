# StratDesk integration decision

## Decision

**Adopt a private, CPU-only chart-analog pipeline now; conditionally adopt bounded historical backtesting after licensing clearance; adapt native UI and evidence-review ideas only; defer or skip the remaining candidates.** This improves the existing **Expo native** StratDesk app without replacing its fixed starter, six-tab navigation, paper-only posture, encrypted/versioned private uploads, or planned TypeScript/Express/MySQL service. Nothing in this decision authorizes live trading, turns a similarity score into a probability, or introduces a public feed.

The app should remain an Expo Router/React Native client. It should call the existing server when that server is deployed privately; the server dispatches bounded Python jobs and returns authenticated, owner-scoped results. Python/OpenCV, SQLite, vectorbt, QuantStats, and any LLM must **not** run in Expo/React Native. There is currently no published backend, so this is an implementation plan—not a claim that any endpoint, worker, push service, or cloud durability layer already exists.

## Adopt: private visual chart analogs with OpenCV

Add an **opt-in visual-neighbor feature** for an owner's own chart uploads. Use a CPU Python worker using OpenCV 4.5.0+ (Apache-2.0; retain required notices) and its documented `cv2.HOGDescriptor(...).compute()` API to calculate fixed-size HOG descriptors from a standardized plot-area crop. HOG is appropriate as a deterministic first pass; OpenCV also documents Canny and contours for supplemental shape features. Do not treat ORB bytes as cosine vectors: OpenCV's ORB guidance requires Hamming/Hamming2 matching instead. [OpenCV license](https://opencv.org/license/) · [HOG API](https://docs.opencv.org/4.x/d5/d33/structcv_1_1HOGDescriptor.html) · [ORB matching](https://docs.opencv.org/4.x/d1/d89/tutorial_py_orb.html) · [Canny](https://docs.opencv.org/4.x/da/d22/tutorial_py_canny.html)

The worker contract is deliberately narrow: accept an authenticated, existing `source_ref_id` and immutable `source_version`, never a client-declared `owner_id`; retrieve the encrypted authorized source; crop the chart region; grayscale and resize to a fixed geometry (the verified example uses 128×128); reject unreadable, blank/low-variance, non-finite, or zero-norm inputs; L2-normalize the float descriptor; and rank with dot product/cosine only against that owner's descriptors. Store a descriptor version and preprocessing/configuration hash alongside each result so historical vectors can be re-indexed reproducibly when crop rules or HOG parameters change. Return the five highest eligible neighbors plus the source/version, similarity, descriptor version, and any separately recorded historical outcome label. Return **“no reliable match”** if the calibrated score or margin threshold is not met.

Use **two stores with different roles**. A local SQLite `chart_vectors` BLOB index is the real, fast, CPU-worker search index for an initially small owner library; all SQL reads/writes must bind `owner_id`, and the worker must use parameterized queries and a composite owner-scoped key/index. SQLite transactions are atomic, while WAL permits concurrent readers with one writer but is only suitable on the same machine/shared-memory environment and requires SQLite-aware handling of database, `-wal`, and `-shm` state. [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html) · [SQLite WAL](https://www.sqlite.org/wal.html)

In addition, make the existing managed **MySQL database the durable, owner-isolated descriptor mirror**. Persist, at minimum, `owner_id`, `source_ref_id`, `source_version`, `descriptor_version`, configuration hash, normalized descriptor BLOB, status, timestamps, and provenance; link to the existing encrypted upload rather than copying raw images. Write the MySQL mirror through an idempotent job/outbox flow, then populate or refresh SQLite from that canonical mirror. The two databases cannot form one distributed transaction, so record a retryable job state and permit SQLite to be rebuilt from MySQL after a worker/container loss. Place SQLite only on an encrypted durable volume if it must survive restarts; do not mistake a container filesystem for durable storage. Protect MySQL backups and the SQLite volume/WAL sidecars, and authorization-test cross-owner read, write, delete, retry, and rebuild paths.

Initial operating bounds are: one fixed descriptor geometry; server-side MIME/byte/dimension validation; a bounded queue and worker concurrency; per-job CPU/time limits; `top_k <= 5`; and at most **2,000** owner candidates for the first linear cosine scan, matching the verified starter pattern. Reject/queue rather than scan beyond the cap; introduce an ANN index only after measured per-owner scale requires it. These bounds, and calibrated no-match thresholds, must be load-tested and benchmarked with labeled chart pairs before rollout. HOG/edges capture visual geometry—not instrument, timeframe, FVG semantics, confluence, or likely performance. Theme, axes, overlays, candle colors, scaling, and bad crops can dominate the score. Display results as **historical visual neighbors**, never as setup certainty, a trade instruction, or a win probability.

A proposed internal API surface, to be implemented only behind the existing authenticated Express service, is: `POST /api/v1/chart-analogs/index` with a source reference/version (enqueue); `GET /api/v1/chart-analogs/jobs/:jobId` (owner-scoped status); and `POST /api/v1/chart-analogs/search` with a source reference/version and bounded `top_k` (results only). These are internal product contracts, not third-party APIs and not public endpoints. The Expo client supplies no storage credentials and never supplies an owner identifier.

## Conditionally adopt: bounded vectorbt + QuantStats historical analysis

Subject to written legal/product clearance, add a separate Python historical-analysis job using community vectorbt's documented `vbt.Portfolio.from_signals(...)` / `from_orders(...)` simulation APIs and `vbt.RollingSplitter().split(...)` or `ExpandingSplitter` to construct splits. Use QuantStats only on a dated portfolio-return series—e.g., `qs.reports.html(pf.returns(), benchmark_returns)`—for a separate report/tear sheet. vectorbt documents portfolio simulation, parameter sweeps, splitters, and a QuantStats adapter; QuantStats explicitly distinguishes return-period measures from discrete-trade outcomes. [vectorbt usage](https://vectorbt.dev/getting-started/usage/) · [portfolio API](https://vectorbt.dev/api/portfolio/base/) · [splitters](https://vectorbt.dev/api/generic/splitters/) · [QuantStats repository](https://github.com/ranaroussi/quantstats) · [QS adapter](https://vectorbt.dev/api/returns/qs_adapter/)

Do **not** represent vectorbt community tooling as PRO. Community splitters create the ranges; StratDesk must implement the chronological loop itself: for each fold, fit/select parameters only on the earlier training segment, freeze them, and evaluate once on the later test segment. Persist the exact train/test boundaries, source-reference versions, approved parameter set/grid, strategy code version, feature/preprocessing version, price/execution assumptions, fees, slippage, and generated trade records. Signals based on bar *t* close must be shifted to *t+1* and simulated at a defensible next-bar execution price; that shift does not fix future-dependent features, revised data, or improperly fitted preprocessing. Include fees/slippage, but label them as a limited execution model rather than proof of live fill quality.

Run this only as an opt-in server job against owner-authorized historical OHLCV and approved parameter inputs. Cap date range, symbol count, parameter-grid cardinality, memory, wall time, queue depth, and output size; store outputs in owner-scoped MySQL records with reproducible run metadata. Return simulated metrics, assumptions, folds, and vectorbt trade records. Label period-return reporting separately from trade-level results, use trade records for trade-level wins/losses, and label every report **historical/simulated—not a forecast or execution recommendation**.

This is **conditional rather than immediately shippable** because vectorbt community is licensed under Apache-2.0 **with Commons Clause v1.0**, which restricts selling a product/service whose value derives entirely or substantially from its functionality. QuantStats is Apache-2.0. Review the StratDesk commercial/hosted use against the vectorbt terms and obtain an exception or use a cleared alternative before dependency approval; do not call vectorbt unrestricted OSI open source. PRO automated cross-validation, including purging/embargoing, is not included—do not claim it. [vectorbt license](https://vectorbt.dev/terms/license/) · [community vs PRO](https://vectorbt.dev/getting-started/upgrade/)

## Adapt: native presentation and evidence-based discussion

Adapt **presentation patterns**, not the Next.js dashboard itself. Keep Expo Router/React Native and its current theme/navigation; optionally introduce reusable native KPI-plus-sparkline cards, grouped chart panels, and compact/collapsible native navigation where an identified Chart or Markets workflow improves. The reference is a TypeScript Next.js/React Bootstrap/Chart.js template with generic sample admin metrics, so it is design inspiration—not a native component library or trading-data source. Reusing substantial code would require retaining its MIT notice; a separate Next.js dashboard would fragment the native product. [reference repository](https://github.com/kitloong/nextjs-dashboard) · [sample dashboard source](https://raw.githubusercontent.com/kitloong/nextjs-dashboard/main/src/app/%28dashboard%29/page.tsx) · [MIT license](https://raw.githubusercontent.com/kitloong/nextjs-dashboard/main/LICENSE)

If the existing app needs a styling refresh, incrementally add a compatible **stable NativeWind** setup only after checking its Expo SDK, Metro/Babel, and peer dependencies. NativeWind documents `className` styling compiled to native `StyleSheet` objects; Expo notes ordinary Tailwind alone does not support iOS/Android. It is a styling layer, not a component library, data provider, alert system, or logic replacement. Implement expandable journals and sticky sections through React Native list/header behavior as well as styling. In-app alert pills are permitted for validated foreground state; **CSS/NativeWind cannot create remote notifications**, and closed-app delivery requires a separately designed native-push/backend service. Do not add it under this decision. [NativeWind docs](https://www.nativewind.dev/docs) · [installation/status](https://www.nativewind.dev/docs/getting-started/installation) · [Expo Tailwind guidance](https://docs.expo.dev/guides/tailwind/)

Adapt the **idea** of a research-team LLM discussion as a bounded evidence-review flow only, not a claim about TradingAgents, its architecture, its results, or its paper accuracy. The supplied research has no verified paper, linked code, license, or roles, so do not adopt named TradingAgents roles or any purported accuracy result. A future discussion may have three evidence-grounded responsibilities: (1) provenance reviewer, which checks that every claim names an owner-authorized TradeLocker/CB/private-upload source and version; (2) method reviewer, which checks chronology, assumptions, folds, and simulation labels; and (3) analog reviewer, which describes returned visual neighbors and their limitations. It must cite supplied records, identify conflicts/missing inputs, preserve the paper-only boundary, and never manufacture a probability (including **87%**), signal, or trade instruction. Defer a model-provider/API implementation until privacy, retention, cost, and prompt-injection controls are selected; no model SDK or external research-role data has been verified here.

## Skip/defer: TradingView-Screener and unentitled public feeds

**Do not integrate TradingView-Screener** into alerts, FVG/confluence/analog analysis, decisions, LLM context, or any production feature. Its `Query().select(...).where(...).order_by(...).offset(...).limit(...).get_scanner_data()` API returns bounded screener rows/snapshots, not licensed historical OHLC candles or an enhancement of the private TradeLocker account feed. The wrapper is MIT, but that does not grant a license to TradingView/data-provider content. Its documentation notes session-cookie-dependent streaming/delayed modes, a default 50-row limit, and risk of bans from large queries; TradingView terms restrict market-data use to display and prohibit unapproved processing, redistribution, commercial/API use, and third-party services. [wrapper README](https://github.com/shner-elmo/TradingView-Screener) · [wrapper MIT license](https://github.com/shner-elmo/TradingView-Screener/blob/master/LICENSE) · [TradingView policies/terms](https://www.tradingview.com/policies/) · [screener overview](https://www.tradingview.com/support/solutions/43000718885-tradingview-screeners-walkthrough/)

Do not imply an entitlement merely because a feed is publicly visible. There is no verified entitlement in the supplied evidence for TradingView redistribution/processing, real-time scanner data, broader historical bars, news/sentiment, COT, economic-calendar, or other public-feed inputs. The only existing data context is private TradeLocker/CB data and private uploads; continue to obtain/confirm rights, freshness, retention, and redistribution terms for each provider before any new ingestion or display. If written authorization later covers a specific use, assess an isolated, opt-in, visual-only screener with server-held credentials, hard query caps, source/freshness labels, and no signal/alert/AI path.

## Implementation order and exit criteria

1. Deploy no new public surface. Add owner-scoped MySQL schema, encrypted durable worker storage, idempotent job state/outbox, and authorization/rebuild tests; then ship the OpenCV feature behind an opt-in flag.
2. Validate visual retrieval with labeled owner-consented chart pairs, calibrate a no-match threshold, test loss/restart recovery from the MySQL mirror, and confirm that no cross-owner descriptor/result can be read.
3. Obtain vectorbt Commons Clause clearance. Only then build the bounded chronological-fold worker and require its reproducibility metadata before exposing any historical report.
4. Make native UI changes incrementally only where usability testing supports them; leave the native stack and six tabs intact. Defer native push, LLM provider wiring, all unverified TradingAgents roles, and every unentitled feed.

This sequence adds real local OpenCV/SQLite capability and durable managed-DB recovery without overclaiming performance, data rights, paper validation, or backend readiness.
